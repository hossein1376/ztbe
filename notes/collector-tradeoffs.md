# Collector trade-offs: browser vs native agent, per OS

Date: 2026-10-21 (round 2). Decision: **D12** (`notes/decisions.md`). Spec: §3.1–§3.2, §9.3.

Facts below come from the platform documentation named in each row, read on 2026-10-21. **UNVERIFIED** marks behaviour that the docs do not state and that only the capture spike (PLAN M1-T5) can settle.

## 1. What ZTBE needs from a collector

| Need | Why | Spec |
|---|---|---|
| Key down/up timestamps at ≤ 4 ms resolution | Hold and latency features; `rollover_frac` needs ≤ 4 ms | §3 |
| Key **position** (scancode), not the character | Zone mapping, independent of layout and IME, content-blind | §3 |
| Injected-vs-physical provenance | A6, accessibility classes | §3.1 |
| Keyboard device identity | Per-keyboard templates (D-f) | §3.2 |
| Coverage of the whole session, not one site | A4 is a walk-up on the *device* | §2 |
| Survives the user being a non-admin; detectable when stopped | A10 | §9.3, §9.6 |

## 2. Browser (in-page JavaScript or extension content script)

| Aspect | What it can do | Source |
|---|---|---|
| Timestamps | `event.timeStamp` / `performance.now()` are coarsened to **100 µs** (5 µs if cross-origin isolated) "or a higher implementation-defined value". That is fine for keystroke timing. Whether a browser adds jitter is implementation-defined (UNVERIFIED per browser) | W3C HR-Time, "coarsen time" (w3c-hrtime) |
| Key position | `KeyboardEvent.code` gives the physical key (standard DOM; not separately checked here) | — |
| Provenance | `isTrusted` is false only for events dispatched by script (`dispatchEvent`). Events generated by the user agent are trusted. OS-level injected input arrives through the UA as ordinary input, so it is indistinguishable in the page (inference from the definition) | MDN `Event.isTrusted` |
| Device identity | None | — |
| Coverage | Only while the page or extension has focus, and only on sites that embed the collector | — |
| Install and permissions | None for in-page; extension install for the proof relay | — |

**Verdict.** The browser is good for an *RP-scoped* risk signal, which is what fraud vendors ship (`notes/landscape.md`). It is poor for A4 (no global coverage), A6 (no provenance) and D-f (no device identity). It is used in v2 **only as the proof relay** (spec §9.5).

## 3. Windows (native)

| API | What it gives | Caveats | Source |
|---|---|---|---|
| Low-level keyboard hook (`WH_KEYBOARD_LL`, `KBDLLHOOKSTRUCT`) | vkCode, scanCode, flags, time. `LLKHF_INJECTED` (0x10) = injected by any process; `LLKHF_LOWER_IL_INJECTED` (0x02) = injected from a lower-integrity process | `time` is "equivalent to what GetMessageTime would return", i.e. a millisecond tick. GetTickCount resolution is "typically 10 to 16 milliseconds" (ms-gettickcount). This is consistent with the 15.625 ms quantum seen for some Tappy users (inference). **The agent MUST timestamp with QueryPerformanceCounter in the callback.** Callback latency jitter is UNVERIFIED | ms-kbdllhook, ms-gettickcount |
| Raw Input (`WM_INPUT`, `RAWINPUTHEADER.hDevice`) | Per-device identity (multi-keyboard, D-f) | Whether injected input carries a null or zero `hDevice` is UNVERIFIED | Microsoft RAWINPUTHEADER docs |
| `GetSystemMetrics(SM_REMOTESESSION)` | Nonzero inside a Terminal Services client session → do not score (spec §3.1) | Citrix and other VDI detection: UNVERIFIED | Microsoft GetSystemMetrics docs |
| Session placement | Hooks run in the interactive session. Hence the per-session `ztbe-capture` helper plus a LocalSystem service (spec §9.3) | Standard users cannot stop a LocalSystem service. Admins can, which yields SIGNAL_LOST | — |

How on-screen keyboard, dictation and AT tools appear (injected flag set? which process?) is **UNVERIFIED** and is the key spike question for D13.

## 4. macOS (native)

| API | What it gives | Caveats | Source |
|---|---|---|---|
| `CGEvent.tapCreate` (listen-only) | Key down/up events with timestamps and keycodes | Only root may place a tap where HID events enter the window server; other processes tap at session level. The tap is disabled on callback timeout (`tapDisabledByTimeout`), so the helper must re-enable it and report `capture_lost` | Apple CGEvent.tapCreate and CGEventType docs |
| Input Monitoring permission (TCC `ListenEvent`) | Required to receive events "from all processes" | MDM **cannot pre-grant** it. The PPPC payload allows only `Deny` or `AllowStandardUserToSetSystemService`, so a standard user can approve it but must act. This is a deployment cost | apple-pppc (Apple device-management YAML) |
| `kCGEventSourceUnixProcessID` field | Source PID of the event → injected vs HID (spec §3.1) | Value for hardware events vs synthesised events: UNVERIFIED | Apple CGEventField docs |
| Secure Event Input | When an app enables it (password fields, some terminals), other processes stop receiving keystrokes (widely documented behaviour; Apple doc page not retrieved: UNVERIFIED) | Windows of no signal while it is active. The agent MUST report `idle`, not `capture_lost`, if it can detect this | — |
| Device identity | IOHID device (vendor/product ID) via IOKit | Mapping tap events to an IOHID device: UNVERIFIED | — |

## 5. Linux (native)

| API | What it gives | Caveats | Source |
|---|---|---|---|
| evdev (`/dev/input/event*`, `struct input_event { struct timeval time; ... }`) | Kernel timestamps with µs fields, scancodes and key codes, per device node (device identity for free) | Needs root or the `input` group. A root service reading evdev sees **all seats**, so it MUST map devices to the active logind seat and session and drop the rest. Wayland and X11 independent | linux-input |
| uinput | Virtual devices created from userspace | Events from a uinput node = injected (spec §3.1). Distinguishing assistive uinput tools from attack tools needs an allowlist by device name/phys (UNVERIFIED reliability) | linux-input (uinput page) |
| X11 (XInput2 raw events) | Global key events for an unprivileged client | X11 only. Not needed if evdev is used | — |
| Wayland | Clients get key events only for their focused surface; the compositor owns the input devices | No unprivileged global capture by design. Hence the evdev-in-service design | libinput docs ("libinput is not used directly by Wayland applications") |

## 6. Comparison and decision

| Criterion | Browser | Windows | macOS | Linux |
|---|---|---|---|---|
| Timing ≤ 4 ms | Yes (≥ 100 µs coarsening) | Yes, **only with QPC in the callback** (the hook `time` field is 10–16 ms) | Probably (UNVERIFIED) | Yes (evdev µs fields) |
| Provenance | No | Yes (`LLKHF_INJECTED`) | Partial (source PID; UNVERIFIED) | Yes (uinput node) |
| Device identity | No | Yes (Raw Input) | Probably (IOHID; UNVERIFIED) | Yes (evdev node) |
| Global coverage | No | Yes | Yes, after a TCC prompt | Yes (root service) |
| Deployment friction | Lowest | Service install | Service + user TCC approval | Service + seat mapping |

**Decision (D12).**
- Native agent; Windows first, then macOS, then Linux.
- The browser extension serves only as the proof relay.
- A JS collector is deferred to a possible RP-scoped v3 profile.

The capture spike (1–2 weeks) must measure on each OS:
1. timestamp quantum and jitter versus a hardware reference;
2. the provenance seen for an on-screen keyboard, dictation, AutoHotkey-style tools, password-manager auto-type, RDP and VNC;
3. how often capture gaps occur (Secure Input, tap timeouts).
